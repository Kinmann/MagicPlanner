# PRD 작성 원칙

생성일: 2026년 3월 29일 오후 1:41

## 1. 개요 및 위상 (Overview & Status)

- **위상**: 본 문서는 DAG(단방향 비순환 그래프) 파이프라인의 최상위 제네시스(Genesis) 노드임.
- **목적**: 사용자의 비정형/원시(Raw) 요구사항을 시스템이 처리 가능한 계층적, 구조적 데이터로 변환함. 본 문서에서 정의된 모든 데이터와 식별자는 후행 문서(FSD, IA, TC 등)의 절대적인 기준점(Source of Truth)이 됨.
- **Genesis 특권 (Genesis Privilege)**: PRD는 파이프라인 내 유일하게 '창의적 발산(Creative Divergence)'이 허용되는 노드임. 사용자의 원시 요구사항을 바탕으로 하되, 평가 루프(Optimizer)의 피드백에 따라 제품의 가치를 극대화하는 혁신적 기능을 능동적으로 도출할 권한을 가짐.

## 2. PRD 특화 작성 통제 원칙 (Domain Principles)

### A. Genesis Identifier (초기 식별자 부여 규칙)

- **원칙**: PRD는 모든 기능과 요구사항에 대해 후행 문서에서 추적 가능한 고유 식별자(ID)를 최초로 생성하고 부여해야 함.
- **명명 규칙 (Naming Convention)**:
    - Epic 레벨: `EPIC-{NNN}` (예: EPIC-001)
    - Feature 레벨: `FEAT-{NNN}` (예: FEAT-001)
    - Requirement 레벨: `REQ-{NNN}` (예: REQ-001)
- **제약**: 한 번 부여된 식별자는 구조 내에서 절대 중복될 수 없으며, 계층 간 매핑(Mapping)이 명확해야 함.

### B. 요구사항의 계층적 분해 (Hierarchical Decomposition)

- 사용자의 요구사항을 다음의 3단계 뎁스(Depth)로 분해하여 구조화할 것.
    1. **Epic (에픽)**: 제품의 핵심 목표를 달성하기 위한 최상위 기능 그룹.
    2. **Feature (기능)**: Epic을 구성하는 구체적인 시스템 동작 단위.
    3. **Requirement (상세 요구사항)**: Feature를 구현하기 위한 사용자 스토리 및 인수 조건(Acceptance Criteria).

### C. 비기능 요구사항 (NFR) 범용 도출 강제

- 사용자의 원시 요구사항에 비기능적 요소가 누락되어 있더라도, 타겟 시스템의 도메인 특성을 분석하여 다음의 핵심 비기능 요구사항(NFR) 카테고리를 기본적으로 도출하고 명시할 것.
    - **운영/호환성 환경**: 타겟 디바이스, 지원 OS 및 브라우저, 최소/권장 해상도 등.
    - **성능 및 가용성**: 목표 응답 시간, 트래픽 처리 기준, 가동률(Uptime) 등.
    - **보안 및 규정 준수**: 데이터 암호화 수준, 인증/인가 방식(OAuth, SSO 등), 권한 통제 기준 및 개인정보 보호 규정.
    - **데이터 및 인프라**: 데이터 보존 정책, 백업 주기, 네트워크 단절 시 상태 처리 기준 등.

### D. 모호성 배제 및 제약 사항(Constraints) 정의

- **가정(Assumption) 분리**: 사용자의 입력 데이터 중 논리적 비약이나 모호한 부분은 '제약 사항(Constraints)' 또는 '가정(Assumptions)' 블록으로 격리하여 명시할 것.
- **Out of Scope (범위 외)**: 현재 개발 페이즈에서 제외되는 기능을 명확히 서술하여 범위 폭주(Scope Creep)를 사전 차단할 것.

### E. 다중 평가 루프 기반 창의적 확장 (Iterative Creative Expansion)

- **원칙**: 10회 이상의 Generation-Evaluation 사이클을 상정하여, 반복 횟수가 누적될수록 제품의 창의성과 차별성을 고도화하는 방향으로 스키마를 확장함. 단, 사용자의 최초 핵심 의도(Core Intent)를 훼손해서는 안 됨.
- **N-Cycle 진화 매커니즘 (Evolution Mechanism)**:
    - **초기 단계 (1~3회차)**: 원시 요구사항의 충실한 구조화, 기본 기능(Feature) 도출 및 필수 비기능 요구사항(NFR) 정의에 집중함.
    - **중기 단계 (4~7회차)**: `Evaluator Feedback`을 트리거로 삼아 '측면 사고(Lateral Thinking)'를 적용함. 경쟁 우위 확보를 위한 혁신적 UX 제안, 잠재적 페인포인트(Pain-point)를 선제적으로 해결하는 차별화 기능, 예외 케이스에 대한 유려한 처리 방안 등을 신규 `Feature` 및 `Requirement`로 추가 도출함.
    - **후기 단계 (8회차 이상)**: 확장된 창의적 아이디어들의 시스템적 실현 가능성을 점검하고, 데이터 정합성(ID 매핑, 제약 사항 등)을 최종 정제하여 기술 문서로서의 엄밀성을 확보함.
- **창의성과 통제의 분리**: 창의적 제안은 반드시 `description`, `user_story` 등 서술형 데이터 필드 내에서 구체화되어야 하며, 최상위 JSON 스키마 규격과 `Genesis Identifier` 규칙은 어떠한 경우에도 파괴할 수 없음.

## 3. 스키마 매핑 주의사항 (Schema Mapping Notes)

- `Target Schema`에 정의된 `acceptance_criteria` (인수 조건) 배열은 반드시 테스트 가능한(Testable) 형태의 단문으로 작성할 것. (예: "사용자가 유효하지 않은 API Key를 입력하면, 인증 실패 에러 코드를 반환한다.")
- 모든 설명형 텍스트 필드는 공통 규칙의 '명사형 종결 문체'를 엄격히 적용할 것.
