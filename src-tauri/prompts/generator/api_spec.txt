# API 명세서 작성 원칙

## 1. 개요 및 위상 (Overview & Status)
- **위상**: 본 문서는 DAG 파이프라인의 일곱 번째 노드임.
- **의존성**: FSD의 `FUNC-{NNN}` 식별자 및 로직, ERD의 데이터 스키마를 핵심 입력원으로 함.
- **목적**: 클라이언트-서버 간 데이터 교환을 위한 RESTful 인터페이스 규격 정의.

## 2. API 명세서 특화 작성 통제 원칙 (Domain Principles)

### A. 이전 설계 계승 및 발전 (Refinement)
- 만약 `$PREVIOUS_DRAFT`에 데이터가 존재한다면 이를 기본 골격으로 삼으십시오.
- `$EVALUATOR_FEEDBACK`의 내용을 분석하여 결함 사항을 최우선으로 교정하고, 기존의 정합성 있는 엔드포인트 및 필드 규격은 최대한 유지하십시오.

### B. RESTful 아키텍처 제약 (RESTful Design Constraints)
- **URI 설계**: 자원 중심 명사(복수형) 구성. ERD의 `table_name` 차용 (예: `/api/v1/users`).
- **HTTP 메서드**: GET(조회), POST(생성), PUT/PATCH(수정), DELETE(삭제) 표준 준수. 행위는 URI에 포함 금지.

### B. 데이터 정합성 보장 (Data Consistency)
- **기능 매핑**: 모든 엔드포인트는 FSD의 `FUNC-{NNN}`과 1:1 또는 N:1 매핑 필수.
- **파라미터 통제**: 요청/응답 페이로드 필드는 **ERD의 `column_name` 및 타입과 100% 일치**해야 함.
- **제약 조건**: ERD의 `Nullable`, `Length` 등 제약 사항을 유효성 검증 규격으로 반영. 임의 필드 창작 엄격 금지.
- **명명 규칙**: Key는 **영문 소문자 스네이크 케이스(snake_case)** 고수.

### C. 권한 및 보안 명세
- FSD의 `pre_condition`에 따라 인증 토큰(Bearer Token 등) 요구 사항을 `Headers`에 명시.

### D. 예외 처리 표준화
- FSD의 `Exception Flow`를 분석하여 표준 HTTP Status Code 할당:
    - 200/201/204: 성공
    - 400: 잘못된 요청 (Validation 실패)
    - 401/403: 인증/인가 실패
    - 404: 자원 없음
    - 409: 리소스 충돌

## 3. 스키마 및 데이터 작성 규칙
- **파라미터 분류**: Path Params, Query Params, Request Body로 명확히 구분.
- **페이징 규격**: 목록 조회(GET) 시 `limit`, `offset`, `sort` 파라미터 필수 포함.
- **응답 정규화**: `status`, `message`, `data` 구조의 일관된 JSON 래퍼 사용.
- **JSON 문자열 고수**: `request_body`와 `responses.schema` 필드는 반드시 **유효한 JSON 형식의 문자열**로 작성해야 함. (예: `"{ \"key\": \"value\" }"` 형식)
