## [SAD - Module Split 설계 원칙]
1. **토폴로지 설계**: 모듈 간의 연결망을 식별자 관계(`MOD-A` -> `MOD-B`)로 정의하십시오.
2. **식별자 상속 및 정합성**: 
   - 의존성 정의 시 **반드시** `$PREVIOUS_ARCHITECTURAL_DECISIONS.sad_module_list` 노드에서 새롭게 정의되고 확정된 `module_id`만을 사용하십시오. 
   - 상위 노드인 `sad_module_list`에 존재하지 않는 ID를 임의로 참조하거나 이전 단계의 세분화된 ID를 사용하지 마십시오.
3. **순환 참조 방지**: 순환 참조(Circular Dependency) 구조가 발생하지 않도록 의존 방향성을 엄격히 통제하십시오.
4. **글로벌 규격 준수**: 통신 방식 정의 시 선행 확정된 `Global Context`와 `Genesis PRD`의 프로토콜 규격을 반드시 매핑하십시오.
5. **이전 설계 계승(Refinement)**: `$PREVIOUS_DRAFT`에 데이터가 존재한다면 이를 기본 골격으로 삼고, `$EVALUATOR_FEEDBACK`의 교정 지시 사항을 최우선으로 반영하여 의존성 및 통신 규격을 개선하십시오.

## [모듈 의존성/통신망 정의 규칙]

1. **의존성 그래프 (DAG)**:
   - 모듈 식별자 간의 참조 방향성을 명확히 정의하여 유향 비순환 그래프(DAG) 구조를 산출하십시오.
   - **양방향 및 순환 참조 금지**: 모듈 간 `A <-> B` 형태나 `A -> B -> A` 형태의 순환 고리가 발생한다면, 이는 모듈이 잘못 분리된 것입니다. 이 경우 해당 모듈들을 하나로 병합하여 구조적 결함을 제거하십시오.

2. **통신 방식 (Communication Protocol)**:
   - 각 의존성 링크에 선행 확정된 `Global Context` 규격에 맞는 통신 방식(예: `SYNC_REST`, `ASYNC_KAFKA`) Enum을 명시하십시오.

3. **고립 방지**: 모든 모듈은 시스템 전체 토폴로지 내에서 최소 하나 이상의 Inbound 또는 Outbound 의존성을 가져야 합니다. 단독 실행 마이크로서비스가 아니라면 고립된 모듈은 존재할 수 없습니다.

```json
      "description": "..."
    }
  ]
}
```
